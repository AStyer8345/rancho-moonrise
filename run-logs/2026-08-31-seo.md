## The safari-tents indexing question is now closed on the on-site side

`/safari-tents-near-austin/` has ridden the NEEDS ADAM list for months, now ~126 days uncrawled. Re-verified still true this run, in the **strongest form yet**: a topically-exact `site:ranchomoonrise.com safari tents` query returned **8 owned URLs** — including `/accommodations/`, whose title is literally *"Safari Tents & Cabins"* — and never the dedicated page.

Rather than report that for a ninth consecutive run, this run diagnosed it. **Every on-site hypothesis is now disconfirmed:**

| Hypothesis | Test | Result |
|---|---|---|
| Page is orphaned | count inbound internal links | **5 public inbound** — *identical* to `wedding-venues-near-austin` (5) and `corporate-retreat-near-austin` (5), both indexed and ranking |
| Missing from sitemap | grep `sitemap.xml` | present, line 145 |
| Broken route | `curl` live | **200** |
| Canonical / URL-form mismatch | compare hrefs, canonical, `og:url`, sitemap, `vercel.json` | **all five agree** on `/safari-tents-near-austin/` |
| Not in the blog discovery path | grep `blog.html` | present, 3 references |
| Schema/AEO defect | `validate:site` + JSON-LD parse + `aeo-block` | clean; `aeo-block=2`, `speakable=2` |

One structural oddity was found and cleared: this page sits at the **root** (`/safari-tents-near-austin/`) while every other blog post is at `/blog/<slug>/`. That looked like a promising cause — internal links pointing at a URL form the canonical disagrees with would explain a crawl failure. It isn't: all 7 inbound hrefs use the root form, the canonical and `og:url` use the root form, `vercel.json` routes the root form, and `/blog/safari-tents-near-austin/` correctly 404s. The page is internally consistent; it is simply *shaped* differently from its peers.

**Conclusion, recorded so no future run re-investigates:** there is no on-site defect causing this. The page is as well-linked, well-formed and well-schema'd as two peers that Google indexed and ranked. The remaining explanation is Google-side crawl priority, and the only remaining lever is the 2-minute URL-Inspection → Request Indexing action already sitting at the top of NEEDS ADAM. **Do not queue further on-site work against this URL.**

This is consistent with — and independently reproduces — the task's accumulated finding that on-page levers are measured dry on this property. Four were already disconfirmed (internal-link depth, word count + schema depth, exact-match title/H1, whole-site schema coverage). This adds a fifth data point from a different angle: a page can be on-page-identical to a ranking peer and still not be crawled.
